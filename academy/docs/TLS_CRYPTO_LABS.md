# Cryptography & Secrets Foundations — Instructor Notes (v1.6)

## How to approach the labs

All exercises are browser-only and start with an **empty command editor**. Enter the commands yourself; paste does not count towards completion. A true terminal is not created: the restricted training interpreter recognizes selected OpenSSL-style and CyberLab commands. The X.509 CSRs, certificates, ECDSA key pairs and signatures are generated by **real WebCrypto** and can be exported as real PEM. The TLS 1.3 timeline, NGINX deployment, and secrets store are **teaching simulations**. Use throwaway demonstration material; no production secrets.

## 1. Keys, certificates and trust

- **Private key**: must remain secret, used to sign a TLS authentication proof or other signed data. In an ECDSA certificate, the key does *not* encrypt all HTTPS records.
- **Public key**: can be distributed; used to check signatures. An X.509 certificate associates it with a subject name/identifier, usage restrictions, and an issuer signature.
- **CA**: certificate-issuing authority; its private key signs leaf certificates. A self-signed root is only trusted by clients if explicitly configured as a trust anchor. **Never install the training CA into your OS/browser's general trust store.**
- **CSR**: a PKCS#10 signed request containing the requested identity and a public key; a CSR itself is *not* proof of CA authorization.
- **Subject Alternative Name (SAN)**: holds DNS hostnames authorized by a certificate. Modern HTTPS name checks should use SAN, not simply the CN.
- **X.509 v3 leaf**: has `CA:FALSE`, `digitalSignature`, and TLS Web Server Authentication EKU, signed with ECDSA/SHA-256 in this lab.
- **Validation**: correct signature and trusted issuer, validity period, hostname SAN, and permitted usage. A real client also considers path constraints, chains, permitted algorithms and applicable revocation policy. The browser exercise performs a deliberately bounded subset; OpenSSL can independently verify its output.

### Recommended practical sequence

```
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -keyout root.key -out root.crt -subj "/CN=CyberLab Root CA" -days 365 -nodes
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out server.key
openssl pkey -in server.key -pubout -out server.pub
openssl req -new -key server.key -subj "/CN=training.cyberlab.test" -addext "subjectAltName=DNS:training.cyberlab.test" -out server.csr
openssl x509 -req -in server.csr -CA root.crt -CAkey root.key -out server.crt -days 30 -copy_extensions copy
openssl x509 -in server.crt -text -noout
openssl verify -CAfile root.crt -verify_hostname training.cyberlab.test server.crt
```

The commands above are compatible with OpenSSL 3. They create a locally trusted test chain *only when the root CA file is explicitly passed as the trust anchor*. `-copy_extensions copy` matters: without it, the issuer step might omit the requested SAN, resulting in a certificate that fails hostname verification. The demo CA private key is generated without a passphrase **only to simplify the disposable lab**: in a real CA, protect keys at rest, restrict issuance authority and consider hardware-backed keys.

### Live deployment vs training model

The `lab nginx --host training.cyberlab.test --cert server.crt --key server.key` action produces a **sample configuration**; it does not configure a real web server or create a TLS connection. The server should present its **leaf certificate**, usually with intermediate certs, and use the **matching private key**; clients trust their chosen root CA. A CA private key must never be copied to the web server as its TLS identity key.

## 2. TLS 1.3 — what actually happens

Conceptual sequence:
1. Client sends `ClientHello`, supported versions, SNI, cryptographic key shares, and cipher choices.
2. Server responds with `ServerHello`, selects parameters and sends its ephemeral key share.
3. Server provides EncryptedExtensions, certificate information, CertificateVerify and Finished messages (the precise variants depend on TLS settings).
4. Client verifies identity and trust, validates the handshake signature, and sends Finished.
5. Both parties derive record-protection keys using **HKDF** bound to the authenticated handshake transcript. Application data uses authenticated encryption (AEAD), such as AES-GCM or ChaCha20-Poly1305.

**The lab does not implement TLS 1.3.** The `tls handshake` command performs real browser ECDH only to show that independent peers derive the same shared material, and performs a real signature verification against the lab-issued certificate; the surrounding TLS transcript is an explanatory simulation. No network socket opens. ECDH on its own does not authenticate peers.

### Troubleshooting scenarios

- Wrong SAN: signature may be valid, but `--host intruder.cyberlab.test` must fail.
- Expiration: a certificate outside its notBefore/notAfter window must fail.
- Untrusted root: an otherwise correctly signed cert must fail if root trust is not configured.
- Missing intermediate: full PKIX trust-path validation can fail even if the leaf's DNS SAN is correct.
- SSL/TLS interception: enterprise gateways can replace server certificates using a **separately trusted inspection CA**. Certificate verification should not be disabled to get around misconfiguration.

## 3. Signatures, symmetric cryptography and key agreement

- `openssl dgst` commands perform **actual WebCrypto ECDSA signing and verification**, not the OpenSSL executable. The displayed signature is WebCrypto raw P-256 `(r||s)` form; an actual OpenSSL `dgst -sign` output is DER-encoded. Do not treat the displayed Base64 as a byte-for-byte OpenSSL signature file.
- `webcrypto aes-key`, `encrypt`, `decrypt` perform real AES-256-GCM encryption/decryption with a new random 96-bit nonce. Reusing a nonce with the same AES-GCM key is dangerous. The key is non-exportable and discarded with the lab session.
- `webcrypto ecdh` performs P-256 shared secret agreement. This produces **raw key material** rather than a production traffic key; in authenticated protocols derive session keys through a properly specified KDF and protocol construction.
- `openssl rand -base64 32` uses cryptographically secure randomness via `crypto.getRandomValues` rather than OpenSSL's executable RNG. For real Linux command-line work, use the actual `openssl` program.

## 4. Secrets management and APIs

The in-memory **mock secret store** demonstrates:
- Creation of a high-entropy token restricted to `inventory:read`.
- Authenticated read use and denial of a write request using the same token.
- Rotation replacing old credentials, and revocation denying subsequent use.
- Identifying a fake hardcoded secret in `settings.json` vs a safer server-side runtime reference in `safe.json`.

This is **not a real secrets manager**. Token values are never transmitted. In a production system use a proper secret management platform and enforce scope on the API server. Do not put production tokens into code, public repositories, browser storage, the frontend bundle, `VITE_` variables, logs, or screenshots. A secret that becomes part of client-side JS is exposed to users.

## 5. Verification and limitations

- A real X.509 root + leaf certificate and a real PKCS#10 CSR are created in browser memory. You can export their PEM files and inspect them with OpenSSL on Ubuntu.
- The browser's `verifyIssued` checks the crypto signature, local CA trust decision, expected DNS SAN and time window. This is **not a complete RFC 5280 PKIX validator**; use OpenSSL or another standard PKI library for actual trust-path validation.
- The exercise interpreter intentionally supports a narrow set of commands and fixed filenames, and does not execute host shell code or run NGINX.
- Only practice completion and selected lesson ID are kept in localStorage. Generated keys and demo secrets are ephemeral.
- WebCrypto requires a secure context: HTTPS or localhost.
