# CyberLab v3.0 — one website, one GitHub push

## Recommendation

Use your existing `GabrielReisSantos/gabrielsmind.github.io` portfolio repository as the **single source repository**. Keep the existing Astro portfolio at the repository root, and add CyberLab v3.0 source in a new `academy/` folder. Use one GitHub Actions workflow to compile CyberLab and then copy its static `dist/` into Astro's `public/training/` before the Astro build.

Result:

- `https://www.gabrielreissantos.com/` — existing portfolio, unchanged.
- `https://www.gabrielreissantos.com/training/` — full CyberLab Academy.
- `https://www.gabrielreissantos.com/training/#campaign` — Connected Campaign.

Both are delivered by the same GitHub Pages publication. **No iframe, second host, extra domain, API server or backend needed.** It is one public website with two independently built frontend apps. The hash routes work in a static `/training/` directory; users can bookmark missions.

## After local tests pass: exact integration steps

1. Make a local backup of the portfolio repo and your v2.9 Academy. Export the Academy progress backup from the website/browser first.
2. In the portfolio repo's root, create an `academy/` directory and copy the **complete** v3.0 source there (not the ZIP itself). Avoid copying `node_modules`, `dist`, `.git`, generated `.*-verify` folders, `test-results` or `playwright-report`.
3. At `academy/`, run `npm install`. Commit the resulting `academy/package-lock.json`. At the existing Astro root, keep its original package-lock.
4. In `academy/`, run `npm run verify:all && npm run build`, then install Chromium (`npx playwright install chromium`) and run `npm run test:browser`. Fix any failures **before** deployment. The checks were not run in full in the source-packaging environment due npm registry unavailability.
5. Replace the portfolio's **Pages deployment** workflow with `deployment-portfolio/single-repository-deploy.yml` (copy its contents to `.github/workflows/deploy.yml`). Make sure to disable/remove other workflows that deploy GitHub Pages. Keep other workflows that merely lint/test.
6. Ensure Astro's `public/training/` build output isn't committed: add `/public/training/` to the portfolio root `.gitignore`. Do not delete any other `public` assets. Preserve the existing custom-domain CNAME and DNS configuration.
7. Add an ordinary portfolio navbar link: `<a href="/training/">Cyber Academy</a>`. You may also deep-link to `/training/#campaign`.
8. In GitHub Settings → Pages, choose **GitHub Actions** as the deployment source. Push the combined repo to `main`. GitHub Actions will validate, build, copy and publish both apps in one deployment.
9. Check `/`, `/training/`, `/training/#campaign` and a deep lab link on desktop and mobile. Check browser Console/Network for 404s. Export/import learning progress if changing browser origin; progress is browser-local.

## Why not move CyberLab components into Astro?

There is no need to rewrite the Vite/React app or render it directly inside an Astro page. Separate build boundaries make migrations safer, preserve the existing simulation engines and keep the portfolio fast. One repository and one deploy **does not require one frontend framework**.

## Alternative — two source repositories, still one public site

If you want independent permissions and release history, keep CyberLab in `GabrielReisSantos/cyberlab-interactive` and the portfolio in its existing repo. The existing `deployment-portfolio/deploy.yml` from the Academy can check out both repos, build Vite and embed its `dist/` into Astro `public/training/`. This still produces one public site. The downside is managing synchronized releases and separately pinned revisions. For your current project, **one repo is the simpler deployment path**.

## Security, privacy, limitations

- The Academy is a static client-side simulator. **Never put authentic malware, credentials, privileged APIs, confidential enterprise configs or PII in public source.** Public GitHub and Pages have no secret storage boundary for bundled JavaScript.
- API keys in Vite's browser source/environment are public, even when injected at build time. The simulated token in the campaign is fictional.
- Scores and simulated evidence are browser-local and cannot be treated as tamper-resistant certification records.
- `localStorage` progress is tied to the browser origin; export progress before changing domain/origin or clearing browser storage.
- Pull requests and branch protections are recommended before enabling automated main-branch deployment.
